## Gilded Rose — Pre-Refactoring Analysis

### A note on terms

- SellIn: the number of days left to sell an item.
- Quality: how valuable the item is.
- "SellIn before an update": the code checks the day's rules using the SellIn value the item had at the start of the day, then reduces SellIn afterward. So the branch for "expired" items (`SellIn < 0`) uses the already-lowered SellIn. I point out below exactly where this matters.
- Approval test / snapshot: a test that runs the program and compares its printed output against a saved text file (the `.verified.txt`). If the output differs, the test fails.

### 2. Current rules by item category (using SellIn before the update)

The one loop in `UpdateQuality` handles every item. The important detail is the order of operations each day:

1. Adjust Quality based on the day's rules (using current SellIn).
2. Lower SellIn by 1 (except Sulfuras).
3. If the (now-lowered) SellIn is below 0, apply a second Quality adjustment.

Here is what each category does, category by category.

**Normal items** (e.g. "+5 Dexterity Vest", "Elixir of the Mongoose", and also "Conjured Mana Cake" today, because nothing special matches its name)
- Quality drops by 1 each day, but never below 0.
- After the sell date passes (SellIn was 0 at start of day, becomes negative), Quality drops by 2 per day (1 in the first block, 1 more in the expired block), still floored at 0.
- SellIn drops by 1 each day and can go negative.
- Concrete example from the snapshot: Elixir 5/7 → 4/6 → ... → at SellIn 0 it is 2 quality, next day SellIn -1 quality 0 (dropped by 2).

**"Aged Brie"**
- Quality increases by 1 each day, capped at 50.
- After the sell date passes, it increases by an extra 1 (so +2 per day), still capped at 50.
- SellIn drops by 1 each day.
- Example: Brie 2/0 → 1/1 → 0/2 → -1/4 (jumped by 2 once expired), and later climbs to 50 and stays.

**"Sulfuras, Hand of Ragnaros"** (legendary)
- Quality never changes. SellIn never changes.
- In the data it sits at Quality 80 forever, and both the SellIn 0 and SellIn -1 rows stay fixed.
- Important: the code does not force Quality to 80. It simply never touches Sulfuras. So if a Sulfuras were created with a different Quality, the code would leave that value unchanged. This matters for the rule "do not add automatic corrections."

**"Backstage passes to a TAFKAL80ETC concert"**
- Quality increases by 1 each day normally.
- When SellIn is less than 11 (10 or fewer days), it increases by an extra 1 (so +2).
- When SellIn is less than 6 (5 or fewer days), it increases by yet another 1 (so +3 total).
- All increases capped at 50.
- After the concert (SellIn goes below 0), Quality drops straight to 0.
- Example from snapshot: pass 10/49 → 9/50 (would be +2 but capped at 50); pass 5/49 → 4/50; and a pass that reaches SellIn 0 at quality 50 becomes -1/0 the next day.

**"Conjured" — this is the NEW requirement, NOT current behavior**
- The requirement says Conjured items should degrade twice as fast as normal items.
- The current code has no Conjured logic. "Conjured Mana Cake" is treated as an ordinary item and loses only 1 per day (2 after expiry). The snapshot proves this: Conjured Mana Cake 3/6 → 2/5 → 1/4 → 0/3 → -1/1 (drops by 2 only after expiry, exactly like a normal item).
- So the saved snapshot reflects the current buggy Conjured behavior. When you add Conjured support later, this snapshot's Conjured lines will change, and that change is expected and must be explained (per the steering rules).

### What are the current problems

Looking at the original `UpdateQuality`, the logic is correct but hard to read. The specific problems:
